\subsection{Spaced Repetition Implementation}
\label{sec:impl_sr}

The spaced-repetition subsystem implements the SM-2 model and its extensions in \path{abridgeai/features/spaced_repetition/}. The main implementation layers are the pure scheduling core, the review transaction, the lesson-unlock read model, the due-card worker, and instructor analytics. The full formulas and process diagrams are specified in Appendix~\ref{appendix:algorithm}; this section records the production composition and its main safeguards.

\paragraph{Scheduling core and review transaction}
The pure \path{sm2/} functions derive $Q$ from correctness, hint usage, and response-time ratio, update the Easiness Factor, schedule the next interval, apply jitter, and enforce the interval ceiling. They have no database or network dependencies and are unit-tested at the threshold values for response time, repetition count, and $Q$. The review service loads or initialises the student's card state, applies these functions, writes the updated state and an immutable before/after \texttt{CardReview} row in the caller's transaction, and returns pending events for dispatch only after commit. Consequently, a failed transaction cannot leave either a partial schedule update or a learner-visible notification.

\paragraph{Assessment and lesson progression}
Assessment quizzes do not create new review cards, while existing card evidence is still graded. Lesson unlock is implemented by \path{sm2/lesson_unlock.py} as a read-side gate combining lesson prerequisites, EF coverage, and the optional interview-pass requirement described in Section~\ref{sec:individualised_modeling}. Figure~\ref{fig:lesson_unlock_gate} in Appendix~\ref{appendix:algorithm} shows the complete gate. The implementation returns both the verdict and the blocking evidence used by the learner interface; it does not persist an unlock event.

\paragraph{Reminders and analytics}
The hourly worker in \path{features/spaced_repetition/workers/scan_due_cards.py} scans cards with \texttt{due\_at <= NOW()} and sends at most one in-app reminder per student within the configured cooldown. The quiz-level reminder flag determines whether a student is eligible for a reminder, while the reported count remains the student's full due backlog. Instructor endpoints expose at-risk students, review compliance, and class-level knowledge-retention distributions through the feature's SQL queries.

\paragraph{Robustness and end-to-end cycle}
Beyond textbook SM-2, the implementation bounds EF, dampens positive growth for guessable formats, clamps untrusted response times, and clamps teacher-provided initial EF values before persistence. The resulting cycle is: a graded response produces $Q$, the card state determines the next review, and the due-card worker later reads that state to issue a reminder. Unlock is evaluated separately from the same persisted card state on the learner's next request, so scheduling and progression use one current source of truth without duplicating the algorithmic specification.
