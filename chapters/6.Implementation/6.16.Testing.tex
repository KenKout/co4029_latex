\subsection{Testing}
\label{sec:impl_testing}

Verification of this system is documented in four places, and it is worth
stating once which owns what. Section~\ref{sec:impl_testing} --- this one ---
describes how the implementation is verified: the layers the suite is built
from, what each layer can establish that the others cannot, what the suite
measures, and what is deliberately left outside it. The test cases themselves,
traced to the requirements they discharge, are designed in
Section~\ref{sec:testcase_design} and listed in full in
Appendix~\ref{appendix:testcases}; the per-case execution detail behind the
totals reported here is in Appendix~\ref{appendix:implementation}. Quality
attributes --- latency under load against the non-functional targets, frontend
audit scores, and generated-question quality --- are not verified by this suite
at all: they are measured, and those measurements are Chapter~\ref{sec:evaluation}'s.

\subsubsection{Test architecture}

The suite is layered by what each layer is able to prove, not by the packages
it happens to cover. The distinction that matters most is between the tests
that may touch a database and the tests that may not.

\begin{table}[H]
\centering
\caption{Test layers, what each establishes, and what it requires to run.}
\label{tab:test_layers}

\begin{tabular}{|>{\raggedright\arraybackslash}m{0.17\textwidth}|>{\raggedright\arraybackslash}m{0.40\textwidth}|>{\raggedright\arraybackslash}m{0.22\textwidth}|c|}
\hline
\textbf{Layer} & \textbf{What it establishes} & \textbf{Requires} & \textbf{Files} \\ \hline

Frontend unit / component & Component rendering, hook state machines, guard and invalidation wiring, formatting and i18n integrity. & jsdom, requests intercepted at the network boundary & 229 \\ \hline

\end{tabular}
\end{table}

The split between the first two rows is the load-bearing one. A unit test that
stubs the session can assert that a service calls what it should and in what
order --- the commit-then-dispatch ordering the notification path depends on is
verified exactly this way --- but it cannot establish that a constraint fires,
that a cascade reaches the rows it should, or that two concurrent writers reach
a consistent state. Those properties do not exist in Python; they exist in
PostgreSQL, and the tests that assert them run against a real instance with the
migrations applied. The architectural layer is the unusual one: rather than
testing behaviour, it walks the route table and the model registry to assert
that no route escapes organisation scoping and no write escapes the audit
trail, so an invariant that would otherwise depend on a reviewer noticing fails
the build instead.

\subsubsection{Continuous integration and excluded suites}
\label{sec:impl_ci}

The ordinary command is \texttt{uv run pytest}. In continuous integration the
migrations are applied before a single coverage run:

\begin{verbatim}
uv run alembic upgrade head
uv run pytest --cov=abridgeai --cov-report=xml \
  --cov-report=term-missing --cov-fail-under=75
\end{verbatim}

The CI environment provides PostgreSQL and Redis service containers, and the
job sits alongside linting and security scanning as a required gate. The
frontend equivalents are \texttt{npm run test:run} for the unit and component
suite and \texttt{npm run test:e2e} for the browser suite.

Three things are deliberately outside the gated run. The \texttt{voice\_live}
marker guards an opt-in harness
(\path{tests/integration/test_voice_live_harness.py}) that drives English and
Vietnamese LiveKit scenarios end to end, checking audible agent output,
persisted turns and cleanup; it requires \texttt{RUN\_LIVEKIT\_VOICE\_TESTS=1},
LiveKit credentials and a live model endpoint, so it consumes paid external
services and cannot be a per-commit gate. The \texttt{destructive} marker
guards tests that reset shared state. The Playwright suite needs a browser and a
running stack, so it is executed against the deployed environment rather than in
the per-commit unit job; the end-to-end column of
Table~\ref{tab:test_results} reports that run. The resulting boundary is
deliberate: deterministic state, persistence and race-safety behaviour is
verified continuously, while live STT, TTS and WebRTC validation remains an
explicit operational test.

That boundary carries a cost worth recording, because it is the one this suite
paid most visibly. An end-to-end assertion is reached only through a chain of
environment --- browser binaries, the backend's signing key and database,
fixture state, and the rendered language --- and a break anywhere along it
surfaces as dozens of failing assertions rather than as one configuration
error. Reading such a run therefore begins by asking whether the failures share
a cause, not by treating them as a list of defects: in practice they rarely
are one.

One limit should be stated plainly, because no quantity of passing tests
addresses it. This suite establishes that the system behaves as specified; it
does not establish that the specification improves learning. In particular the
scheduling model of Appendix~\ref{appendix:algorithm} is verified against its
own definition --- the derivation of $Q$, the ease-factor update, the interval
rules and their boundary conditions --- and not against retention outcomes,
which would require a longitudinal cohort study outside this project's scope.
